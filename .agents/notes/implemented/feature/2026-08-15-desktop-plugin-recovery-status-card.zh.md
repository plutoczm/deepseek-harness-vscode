# Agent Note: Desktop 插件恢复状态卡

Status: implemented

[English](2026-08-15-desktop-plugin-recovery-status-card.md) | 中文

## 问题

F005 暴露带稳定机器原因码、重试权限和诊断导出权限的封闭恢复状态。只显示原始代码的紧凑横幅难以理解，而泛化错误提示又会隐藏支持排查所需的证据。浏览器 fixture 必须呈现同一渲染器合同，但不能暗示自己拥有 Profile 或进程变更权限。

## 决策

插件中心把每个非 `rolled-back` 恢复快照显示为只读目录上方的一张状态卡。恢复进行中与恢复失败使用不同标题、图标、语义颜色和 live region 优先级。状态卡把封闭的每个 `PluginRecoveryReasonCode` 翻译为用户可读说明，同时保留稳定代码和尝试次数作为次级证据。

“重试恢复”保持主操作，“导出诊断”保持次操作。两个按钮只消费现有的仅含 `operationId` 的意图，遵循桥接能力标志，并在任一请求进行时一起禁用。`rolled-back` 响应会移除状态卡，渲染器不会根据按钮点击推断成功。窄窗口下布局收敛为两列，用户要求减少动态效果时停止旋转动画。

## 曾考虑的替代方案

**只在红色横幅中显示原始恢复代码。** 不采用：用户无法在不查看源码的情况下区分完整性失败、Profile 所有权冲突、Host 故障或运行验证失败。

**在插件中心内部用模态框显示恢复失败。** 不采用：变更关闭时目录查看仍然安全，而且阻塞模态框会重复 Desktop 拥有的独立启动恢复页。

**把独立恢复页样式复制到 Web 客户端。** 不采用：独立页面必须在普通 Host 启动前工作，插件中心则必须使用共享 Web 语义 token 与基础组件。

## 验证

组件测试覆盖可读失败证据、稳定原因码、尝试次数、诊断反馈、同操作重试、`rolled-back` 后移除，以及恢复进行中的禁用状态。`pluginCenterRecovery=failed` 继续作为浏览器验收入口，且不会修改 Profile 或文件。

## 后果

恢复失败在保留支持证据的同时变得可理解，Web fixture 也继续诚实表达自己没有系统权限。生产变更已开放，但未解决的恢复失败会阻止下一次操作，直到重试成功。
