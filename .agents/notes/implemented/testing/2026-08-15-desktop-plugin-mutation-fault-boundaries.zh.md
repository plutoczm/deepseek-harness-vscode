# Agent Note: Desktop 插件变更故障边界

Status: implemented

[English](2026-08-15-desktop-plugin-mutation-fault-boundaries.md) | 中文

## 问题

直接构造开放日志的恢复测试可以证明快照重放，但不能证明真实安装与管理执行器在每个变更副作用两侧持久记录了正确状态。即使执行器在没有留下足够重启恢复证据的情况下修改 Profile 或替换 Host，这类测试仍可能通过。

## 决策

`PluginOperationController` 持有一个只通过构造函数注入的故障器，并且只在所选日志点持久落盘后运行。生产组装不提供该参数，渲染器、桥接、环境变量和打包命令都不能选择故障。可信安装与管理执行器在 Host 停止、Profile 或包变更、Host 启动和页面重连后调用 `completeSideEffect()` 追加 `after-side-effect`，且不向渲染器重复发布同一个进度阶段。

恢复矩阵驱动 F003 真实安装执行器与 F004 真实启用、停用、更新和卸载执行器。每个场景在快照后的十一个点注入一次故障，并要求四个 Profile 权威文件逐字节恢复、目标包存在状态恢复、旧 Host/客户端/Skill 证据完全一致、不出现提交标记，且事务以持久 `rolled-back` 终态关闭。

## 曾考虑的替代方案

**继续直接构造日志记录。** 不采用：它只测试恢复消费者，不能证明变更生产者记录了恢复所需状态。

**为每个执行器增加独立故障标志。** 不采用：五个实现容易漂移，而且生产选项会携带测试词汇。由控制器持有的单一测试缝可以观察共享持久状态机。

**通过开发桥接或环境变量选择故障。** 不采用：让渲染器或打包进程访问该能力会产生不必要的生产故障入口。

## 后果

源码矩阵覆盖五类动作与十一个确定故障点，因此未来执行器漏记边界时会在对应位置失败。矩阵比伪造日志执行更多文件系统和 Host 代次操作，但保持无密钥并使用隔离临时 Profile。生产变更继续关闭，直到独立的 Windows x64 包体中断与重启验收通过。
